# Team discussion, Sat 21 Nov ~14:15 (5U AI)

Summary of what the three of us said, then the raw transcript (voice dictation, unedited).
Decisions are what we agreed; open points are still open.

## Decisions

1. **Keep it as simple as possible (Mattia).** Others will over-engineer and be slow and hard to maintain.
   Simple, fast, easy to understand.
2. **Base pipeline (Mattia):**
   1. **LLM call 1:** parse the customer's email (written by a human) into structured, flexible,
      code-readable JSON.
   2. **In parallel, per carrier:** an LLM call to write the bid request where a carrier is only reachable by
      email; a plain API call where there is an API (no LLM); known data where a carrier is only in the
      spreadsheets.
   3. **LLM call** to parse each carrier reply back into JSON.
   4. **Deterministic script (~100 lines):** matches best price and speed to what the customer asked for.
   5. **Last LLM call:** writes the reply to the customer as humanly as possible, then send. Stop.
   No prediction model or training inside this base flow.
3. **LLM as a cheap classifier:** yes/no, right/wrong, **green / yellow / red**. Only **red** gets reasoning,
   with an expensive model (e.g. gpt-6-astra); everything else on cheap models.
4. **Focus on disruptions from the start, not just prices.** A disruption only shows up because our prices stop
   being good, so something must **monitor** that and then find out **what** changed.
5. **Learn from the field:** read the leaderboard after every quote. It shows every team's score and bookings per
   mail (not their answers). If we are bad, change course. Pitch angle: we don't just calculate prices, we learn
   from the competition and from how we perform against others.
6. **Carriers can't be negotiated with** (asked 5U: no). **Customers can reply** ("too expensive"); then we adjust
   the offer or decline.
7. **UI / human emails (Sam) come after the system works.** First it works, then it gets usable.
   No dashboard or human-readable UI needed yet.
8. **Way of working:** Mattia sets the architecture first (~15 min on his branch, then on main). Then everyone
   builds on top of it; agents compare what each of us did and adapt to his foundation.
   Branches, not main, for our own experiments.
9. **Timeline:** first RFQ at 16:00, so ~1.5 h left. Something simple must run in **~45 min**.
   Synthetic data now: fake emails to run through the pipeline.

## Open points

- **Unknown variable / edge case (Jan):** an email contains something the script doesn't cover (oversized cargo
  like a "giraffe", "planes are grounded"). Do we let the LLM **adjust the script** (agent with permission), or not?
  Mattia's answer: the first LLM call is the flexibility layer; read **all** carrier APIs and carrier emails first
  to know every variable/option that can change, so the LLM only fills a JSON with known options and the rest
  stays deterministic. The LLM is one call, not an agent. Not settled; we wanted a second opinion.
- **Do all carriers reply at the same time?** Unknown. Idea: a second system that predicts when and how offers
  arrive, as a differentiator.
- **Jan's prediction model:** trained on live (real-world) news; here we don't know if the world is real or
  simulated, and there is probably too little data to train. Still a possible differentiator ("a prediction model
  for real-world scenarios"). Jan to explain again what exactly he built.
- **Who owns the pricing engine.** Said in the discussion ("I can do"), speaker unclear.
- Margins are out of scope per the 5U brief, but came up (customer pushing price down).
