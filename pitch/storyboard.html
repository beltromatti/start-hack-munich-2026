How it is built

Your question: transitions, which code, React or not, and how pictures and looping animations get packed into one thing that runs in the room and in the browser.

One HTML file, plain HTML, CSS and JavaScript. No React.

  1. The deck has one piece of state: which slide and which beat. React exists to keep many components in sync with changing data. Here it adds about 140 KB and a build step and solves nothing.
  2. The room is the risk, not the code. Hackathon Wi-Fi can drop. A single file with everything inside runs from the laptop disk with zero network.
  3. It already runs this way. pins/deck.html (slide engine, beats, crossfade) and pins/sketch.html (swarm, line boil, chugging S-Bahn) are both plain JS. Merging them is copying sections, not porting.

What would change it: if a slide had to run the real product UI live (Sam's React frontend). It does not. Slide 9 shows a screenshot taken at 10:00, which never fails.

// the whole engine, about 40 lines in deck.html
function go(i, beat = 0) {
  const from = S[cur], to = S[i]
  from.leave?.()                       // stops its rAF loop and pauses its video
  TRANSITION[to.dataset.in](from, to)  // xfade | cut | grow | match | dawn
  to.dataset.beat = beat
  to.enter?.()                         // starts its loop, plays its video from 0
  cur = i
  history.replaceState(null, "", "#" + (i + 1))
}
// → Space PageDown = next beat, else next slide. ← = back. Clicker sends PageDown.
